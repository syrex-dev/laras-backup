# Pertanyaan Terbuka & Asumsi Implementasi E-Office

Dokumen ini mencatat hal-hal yang ambigu, keputusan arsitektur turunan, dan asumsi teraman yang diambil dalam pengembangan E-Office berdasarkan PRD (`e-office.md`).

---

## 1. Daftar Catatan & Asumsi Teknis

| ID | Topik | Situasi / Ambiguitas | Asumsi Teraman yang Diambil |
|---|---|---|---|
| **OQ-01** | **Transisi Kode Blade/Livewire ke React+Inertia** | Repositori saat ini memiliki jejak prototipe berbasis Blade dan Livewire. Permintaan teknis saat ini mewajibkan React + Inertia + TypeScript. | Kita akan menginisialisasi stack React + Inertia + TypeScript secara bersih di `resources/js`, menginstal adapter Laravel Breeze/Inertia React, dan merefaktor route serta controller secara bertahap per domain. File blade lama akan digantikan secara bertahap tanpa merusak riwayat git. |
| **OQ-02** | **Target Database: PostgreSQL (Fallback: MySQL/SQLite)** | Target utama sistem adalah PostgreSQL 15+. Namun pengujian CI/CD atau dev lokal tertentu dapat membutuhkan fallback. | PostgreSQL ditetapkan sebagai **target produksi dan arsitektur utama** (menggunakan JSONB dan GIN Index). Driver MySQL dan SQLite didukung sebagai fallback pengujian unit/lokal melalui *Schema Builder* standar Laravel. |
| **OQ-03** | **Pemisahan Peran (`roles`) vs Jabatan (`positions`)** | Menghindari tumpang tindih antara hak teknis sistem dan posisi birokrasi tata naskah dinas. | `roles` murni mengatur permission akses fitur sistem (Spatie), sedangkan `positions` menentukan unit kerja, rantai paraf, penerima disposisi, dan pejabat penandatangan naskah dinas. |
| **OQ-04** | **Sistem Lisensi (Klien vs Server Billing)** | Server billing langganan berada di luar lingkup aplikasi E-Office. Aplikasi hanya butuh titik temu lisensi. | Dibuat `LicenseService` berbasis interface dengan implementasi lokal/stub yang memvalidasi payload lisensi (JWT/HMAC hash). Mode default instalasi baru adalah paket "Standar" dengan lisensi aktif, disertai fitur input kunci lisensi manual atau verifikasi API mock. |
| **OQ-05** | **Penyedia TTE (Tanda Tangan Elektronik)** | Belum ada akun penyedia TTE eksternal (seperti BSrE, Privy, Peruri) yang dikontrak di awal. | Arsitektur penandatanganan menggunakan pola *Adapter Pattern* (`SignatureProviderInterface`). Di MVP/Fase awal, disediakan adapter: (1) `WetSignatureAdapter` (unggah pindaian tanda tangan basah), dan (2) `InternalQrVerifyAdapter` (stempel hash kriptografis lokal dengan QR token untuk verifikasi halaman publik). Adapter pihak ketiga dapat dipasang kapan saja tanpa merombak modul surat keluar. |
| **OQ-06** | **Perilaku Lisensi Kedaluwarsa** | Apakah saat kedaluwarsa pengguna boleh mencetak atau mengunduh arsip? | Ya, sesuai prinsip "Data Tidak Boleh Disandera" (PRD Bagian 8.9), saat kedaluwarsa sistem beralih ke mode **Baca-Saja (Read-Only) + Ekspor Penuh**. Seluruh request mutasi (POST/PUT/DELETE) ditolak oleh middleware, namun pencarian, pembacaan, dan unduh/ekspor berkas PDF/Excel tetap aktif 100%. |
| **OQ-07** | **Kamus Istilah Dinamis (Terminology)** | Berapa tingkat hierarki dan istilah yang perlu dikonfigurasi? | Disiapkan kamus JSON fleksibel di `institution_profiles.terminology_dict` yang mencakup: `unit_level_1` (mis. Jurusan/Bagian), `unit_level_2` (mis. Prodi/Seksi), `lead_level_1` (mis. Direktur/Rektor/Ketua), `lead_level_2` (mis. Kajur/Kabid), dan istilah persuratan lainnya. UI memanggil helper `useTerminology()` sehingga tidak ada teks jabatan yang di-hardcode. |
| **OQ-08** | **Koeksistensi Tabel Lama `log_aktivitas` vs `activity_logs`** | Prototipe lama memiliki tabel `log_aktivitas` dan trait `Loggable`. Fase 0 memperkenalkan `activity_logs` append-only ber-trigger PL/pgSQL. | Seluruh penulisan baru dialihkan ke `activity_logs` melalui `AuditLogger`. Trait `Loggable` dimigrasikan untuk meneruskan panggilan ke `AuditLogger::log()`. Tabel fisik `log_aktivitas` dibiarkan ada untuk riwayat prototipe tanpa ada penulisan baru dari aplikasi. |
| **OQ-09** | **Pemilihan Library QR Code & PDF Generator** | Pemilihan pustaka naskah dinas dan verifikasi keabsahan dokumen cetak. | Dipilih `simplesoftwareio/simple-qrcode` (render SVG murni tanpa dependensi shell/biner luar, tajam untuk cetak) dan `barryvdh/laravel-dompdf` (templating Blade native + CSS paged media A4, portabel tanpa headless browser/Chromium di server lokal/Windows, ukuran PDF sangat hemat 30–80 KB). |
| **OQ-10** | **Tautan Surat Keluar Balasan pada Disposisi (`surat_keluar_id`)** | Modul Surat Keluar (Fase 3) belum dibangun, namun skema tindak lanjut disposisi memerlukan pencatatan referensi surat balasan. | Disimpan sebagai kolom `surat_keluar_id` (`BIGINT NULL`) tanpa foreign key constraint keras. Ketika Modul Surat Keluar dibangun pada Fase 3, nilai referensi ini dapat langsung diintegrasikan tanpa memerlukan perubahan skema di Fase 2. |
| **OQ-11** | **Siklus Hidup Disposisi Pasca-Masa Jabatan Plt (Pelaksana Tugas) Berakhir** | Apa yang terjadi pada lembar disposisi yang masih terbuka (`status != selesai`) ketika masa penugasan Plt berakhir (`start_date .. end_date` kedaluwarsa)? | Ditetapkan aturan resmi: (1) **Tanggung Jawab**: Disposisi tetap melekat pada pemegang Plt (`delegated_user_id`) yang menerima tugas sampai selesai; (2) **Akses Pejabat Asli**: Pejabat definitif yang kembali aktif memperoleh hak akses **baca-saja (read-only)** untuk memantau; (3) **Pengambilalihan (Takeover)**: Atasan (pemberi disposisi) atau pengelola (`disposisi.kelola`) berhak mengambil alih disposisi (`TakeOverDisposisiAction`) dan mengalihkannya kembali ke pejabat definitif atau user lain, dengan pencatatan audit log lengkap. |
| **OQ-12** | **Peran 'Sekretaris' vs 5 Peran Resmi PRD** | Pada prototipe awal terdapat role 'Sekretaris' dan 'Admin'/'Staf' yang tidak konsisten dengan 5 peran resmi PRD (Admin Instansi, Pimpinan, Kepala Unit, Staf TU, Petugas Arsip). | Role 'Admin' dan 'Staf' dihapus tuntas. Untuk fungsi 'Sekretaris' (penyiapan naskah pimpinan, registrasi surat): fungsi ini diatur murni berbasis **Jabatan Organisasi (`positions`) dan Permission Granular (`surat-keluar.buat`, `surat-masuk.registrasi`)**, bukan role Spatie terpisah. Pengguna bertugas sekretariat diberi role resmi `Staf TU` dengan posisi fungsional 'Sekretaris Pimpinan'. Seluruh otorisasi aplikasi dilarang mengecek `hasRole('Sekretaris')` dan wajib menggunakan pemeriksaan permission eksplisit (`can(...)`). |
